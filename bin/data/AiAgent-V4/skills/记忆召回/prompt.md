# 记忆召回 · 文案与阈值
# 本文件是本插件唯一的配置源：条数、门槛、预算、行模板、标题全在这里。
# 格式：`键: 值` 一行一条；`#` 开头的行是注释（`## 配置` 这种分节标题也是注释）；
#       行内第一个冒号（半角 `:` 或全角 `：`）是分隔符，值里可以再带冒号（如时间格式）。
# 读法：惰性缓存 + 按文件 mtime 失效 —— 每轮不读盘，改完保存下一轮生效，不需要重启。
# Java 里只留「文件读不到 / host() 为 null 时的兜底默认值」，兜底值与下面前几行一一对应。
# 值两端的空格会被去掉；需要尾随空格的模板由 Java 侧补（见「行模板」说明）。

## 备注（不解析，只给人看）
# 开关：false = 本段这一轮不出现（关掉整个召回，不查库）。
# 条数：查 memory 库取回的条数（V3 是 8；★ 批 18 抬到 12 —— 与「追问条数/查询上限」那一档一起抬：
#   查询串变长之后命中面变宽，条数不跟着抬就会出现"查到了但一条都没渲染进来"）。
# 跨群条数：查 grouplog（群聊历史）取回的条数（V3 是 5；★ 批 18 抬到 8，同上一条的理由）。
# 最小查询字数：查询门槛。把「查询过滤正则」命中的字符全去掉之后，剩下的长度达到这个数才检索
#   —— 现在写 2：像「还有吗」「那个呢」这类两字追问也会召回（改之前是 4，那类追问整段不召回）。
#   一个字的语气词（"嗯""哦"）仍然不触发（V3 hasMeaningfulQuery，QQPromptBuilder.java:719-722）。
#   ★ 批 18：判据用的是「追问条数」合并**之后**的串（见下），所以短追问在活跃会话里会被历史补过门槛。
# 查询过滤正则：默认 [\s\p{Punct}]+ 是 V3 原样（只去空白与 ASCII 标点，全角标点不去）。
#   想连全角标点一起去，可改成：[\s\p{Punct}\u3000-\u303F\uFF00-\uFFEF]+（这会偏离 V3 口径）。
# 预算：本段的字符上限，也是 maxChars() 的返回值（★ 批 18：1200 → 2000）。
#   注意：maxChars() 拿不到 Host，所以它用的是「上一次读到的预算」，首次调用前是代码兜底值。
#   ★ 全局注入预算是 ctxBudgetChars（真机现 20000）：本段 2000 是**上限**，不是每轮必付的值；
#   各段上限之和（2000 + 群成员映射 6000 + 情绪 1000 + 用户画像 600 + 点名引用 1200+1000 + 群印象 500
#   = 12300）仍在 20000 以内。全局超限时基板从 **order 最大**的段整段丢，而本段 order=10 是最前的一档
#   ⇒ 本段涨 800 字符不会把任何段挤掉（挤掉别人只会发生在总量真的超过 20000 时）。
# 单条上限：单条记忆渲染前最多保留多少字（V3 是 300，QQPromptBuilder.java:700）。★ 批 18 **不动**：
#   预算抬到 2000 之后，300 字 × 12 条 = 3600 > 2000，真正的约束是段预算（超出丢尾行），
#   单条再抬只会让"少而长的行"挤掉"多而短的行"，与"热召回要看到更多类似事"的方向相反。
# 跨群单条上限：跨群行里的内容最多保留多少字（V3 是 160，UnifiedQQMemoryManager.java:798）。
# ★ 追问条数：查询串里并进"最近几条本会话对话"（批 18 新加，出厂 8；0 = 退回"只有本轮正文"）。
#   只取**本会话**（SQL WHERE session = ?），拿不到会话键就退回只有本轮正文，绝不并别人的对话。
# ★ 查询上限：合并后查询串的字符上限（批 18 新加，出厂 600）。超了保留**最新**的一段；
#   本轮正文本身 ≥ 这个数时一个字都不加（正文不截断）。
#   为什么要有上限：查询串会进 FTS，Store.search 的拆词 OR 层最多 8 项且**均匀采样**
#   （FtsQuery.DEFAULT_MAX_TERMS）—— 串越长，本轮正文的词占的名额越少。所以本轮正文放在串首
#   （采样点含下标 0），并把整串压在 600 以内。
# ★ 窗口剔重（批 18b，**没有配置键**，判据在 MemoryRecallProvider.window/Win 里）：
#   热召回让查询串变长之后，FTS 会命中上一轮刚说过的那条群聊 —— 而它本来就已经由基板注入了
#   （在「本会话最近 N 条聊天记录」窗口里，或被 ChatWindow 的"历史已有"压掉后仍在对话历史里）。
#   于是同一条消息在同一个请求体里出现两次。这一层按**行身份（grouplog.id）**把那几行从本段剔掉：
#   不是"内容看起来像"，所以同一个人两次说一样的话仍然是两条不同的消息。
#   · 窗口大小 = 基板配置 chatWindowSize（**只读那一个真源**，不在这里再立一个键，免得漂）；
#     配置面拿不到 ⇒ 用基板出厂默认 30（宁可少剔、绝不误删）；<=0 = 基板不带窗口 ⇒ 不剔。
#   · 只剔**本会话窗口**那几行：别的群的 grouplog 与 memory 库一个字都不动；
#     跨表主键不可比（dialog 的 42 ≠ grouplog 的 42），所以结构上不会拿私聊窗口的 id 去剔群聊记录。
#   · 剔重发生在取回之后、不回填 ⇒ 那一段可能少于「跨群条数」行（少掉的本来就已在上下文里）。
#   · 还有哪些情况**不**由这一层兜住（同一条消息仍可能在一个请求体里出现两次，已知、未修）：
#     窗口↔历史（ChatWindow 的 best-effort 内容去重，改了 @ 文案或 ts 差超 60s 就漏）、
#     私聊/控制台（窗口与历史同源，基板刻意不去重）、别的群里同样的文本、
#     同内容不同行（重连重放导致两行 msg_id 相同但 id 不同）、
#     记忆段↔用户画像/印象段（两张表各自注同一批 memory 行）、本轮正文↔窗口里的自己那一行。
# 跨群开关：false = 不查 grouplog、不产出跨群那一段。
# 时间格式：{ts} 的格式（ts 是毫秒时间戳）；ts 缺失时 {ts} 渲染成空串。
# 截断尾巴：超长截断后补的字符串（V3 是 "..."）。
# 匿名昵称：跨群行里昵称为空时的替代（V3 用「某人」，UnifiedQQMemoryManager.java:799）。

# 行模板可用占位符（{键} 字面替换，模板里带 $ 也不怕）：
#   memory 行：{ts} {content} {id} {importance} {scope} {scope_id} {source} {tags}
#   grouplog 行：{ts} {content} {id} {group} {qq} {nickname} {name}
#   {name} 与 {nickname} 同值；两个库都有的键（如 {ts}/{content}/{id}）两边都能用。
# 标题 / 跨群标题：整段的小标题（V3 走 labels：title.related-memories=相关记忆、
#   title.cross-group-related=跨群相关群聊记录，PromptManager.heading 会补上 "## "）。
#   留空 = 不打这一行（V3 里标题为空时就不打，QQPromptBuilder.java:698）。
# 说明 / 跨群说明：标题下面的一句引导语（V3 的 memories-ctx.md 第二行是英文
#   "Previously remembered information that may be relevant:"，这里按 S4 的默认做法用中文）。
#   ★ ID-ANCHOR（2026-09-27）：那一句"读法"（只把 [user:本轮说话人QQ] / [group:本群] 当他的事）
#   刻意写在「说明」的**值里**，不写成 `#` 开头的行 —— `#` 行是注释（Cfg.parse 直接 continue），
#   她永远读不到；只有「标题 / 说明 / 行模板」这几项的值会经 pack() 渲染进上下文。
#   「本轮说话人QQ」的**具体号码**由基板每轮注入的 `【本轮说话人】<昵称>(QQ <号>)` 那一行给出
#   （CtxBuild.speakerAnchor ⇄ CtxBuild.ANCHOR_LEAD），本文件是静态配置、拿不到运行时值。
