# 说明
# 启用清理：on / true / 1 才算开；关掉就完全不动库（TTL 不跑）。
# 清理间隔小时：两次 TTL 清理之间的最小间隔（节流闸门 kv sticker:cleanup:last）。
# 保持天数：收藏时间超过这么多天的**可**淘汰（0 = 不按年龄删）。
# 最低保有量：年龄账的底 —— 任何情况下库里"可用"的图不得少于这么多张；
#           淘汰前先数全库可用数，本轮最多删「可用数 - 最低保有量」张（不足就一张都不删，保住最老的）。
#           "可用" = send() 真能挑出去的那一行（file 非空；本地路径形态的文件必须在盘上；
#           自动收的还要求审查判定 safe=true）。
#           ★ 这**一个**判据只由 `StickerCollect.usableOne` 实现，两侧都只调它：
#             计数侧 `countUsable`（年龄账的底）与挑选侧 `StickerSkill.usable` / `pickByMood` / `random`。
#             以前挑选侧只查"file 非空" ⇒ 磁盘账删掉本地文件、又没有 extra.url 的行会被挑中发出去
#             （结果只有"本机图发不出去"或把一条不存在的盘符路径交给 NapCat 两种坏结局）。
# 最多张数：库里最多留几张，超了按 **ts ASC（最旧的先走）** 删到刚好不超过（0 = 不限）。
#           ★甲方 2026-09-16 拍板：**60 张上限**，且淘汰序是**纯滚动（最旧先走）**。
#           ⇒ 池子 = **最近收进来的 60 张**；`uses` 不再参与淘汰顺序（它只影响"发图选中谁"）。
#           实测入站约 1,051 张/天、过完便宜闸门约 585 张/天 ⇒ 60 张的池子会被新图持续滚动替换
#           （全过审的极端假设下约 2.5 小时滚一遍）；`保持天数: 15` 只是**年龄上限**（老图可淘汰），
#           **不等于"一张图能存 15 天"**。这一条是容量决定，不是缺陷。
#           60 张 × 平均 512KB ≈ 30MB ⇒ 远在 `磁盘上限MB: 256` 之下（磁盘账继续兜底"永不超上限"）。
#           三条硬规则在同一个 tick 内的**真实执行顺序**：磁盘账在收集段末尾**先**跑（超 磁盘上限MB 就删文件，行保留）
#           → 再年龄账（超龄的可淘汰，但删到"可用数 = 最低保有量"就停）
#           → 最后行数账（超 最多张数 就按 ts ASC 删到不超过；不受保底约束，因为 60 > 15）。
# 挑选方式：最常用（默认，确定）/ 随机（在候选池里随机一张）。
# 候选池：参与挑选的候选张数（越大越多样，也让随机更有意义）。
#           ★ 随机那一路另有下限 50：真的随机时窗口 = max(候选池, 50)（见 StickerCollect.random），
#             所以 候选池: 8 时随机窗口实际是 50 张（心情匹配那条路才严格按 候选池 取）。
# 默认语境：collect 没给 scene 时用它；它也是空的就回「缺语境」文案。
#           自动收集也用它当最后的语境兜底（否则"只有图、没有文字、又没描述"的会因 scene 为空而不收）。
# 列表条数：list 没给 limit 时的默认条数。

# ---- QQ 侧自定义表情（cf_list / cf_add / cf_del / cf_desc）----
# ★ 这不是"表情包库"，是 **QQ 账号侧的真实资源**：库里的一行是我们这边的一张图（file/hash），
#   QQ 侧的一条自定义表情的身份是 emoji_id + res_id + md5。两者**不并库**：
#   cf_add 把库里的一行推上去，成功后只在**那一行的 extra.cf** 里记下 QQ 侧的标识
#   （不改 sticker 表结构、不新建表）。
# ★ 权限边界（硬）：四个动作**一律只给主人或她本人（MASTER/SYSTEM）**，非主人一律拒
#   （连"读清单"也拒 —— 它在不在 QQ 侧是账号侧的事实）。技能自己先判一道，权限表里另外
#   给这四个 op 各写一行 Ban[ALLUSER]（两道都拒；少一道也拒）。
#   cf_del 额外还要 **confirm 二次确认**（写 confirm: true 或 "yes"/"确认"），少这一项直接拒。
# ★ 添加：目标是库里的 id / hash，或直接给 file（**必须是本机文件**：NapCat 的 add_custom_face
#   要的是它能读到的本地表情文件；URL / fileid 形态直接拒 cf_need_local）。
#   我们顺手把 md5 / file_size / file_name 一起算好传下去。
#   幂等两道：① 本地账 —— 那一行的 extra.cf.md5 与本次相同 ⇒ sticker_cf_exists（一次 NapCat 都不打）；
#             ② 远端账（尽力而为）—— 先问一次清单，命中同一个 md5 ⇒ sticker_cf_exists_remote。
#   可选 desc：添加动作本身不吃描述，拿到 emoji_id + res_id 之后顺手改一次；拿不到就在回执里写
#   desc=pending，让你改用 cf_desc。
# ★ 删除：只认 res_id 与 md5（上游 delete_custom_face 的字段就是这些，没有 emoji_id）。
#   库里那一行没记过 extra.cf ⇒ cf_not_linked（不拿 md5 猜一个去删）；删掉后只摘掉那一行的
#   extra.cf，**不删本地那一行**（库里那张图还在）。
# ★ 描述：desc 不长于 200 字；**先过内容闸**（标记族 / 内部事实行 / 红线词 —— 与出站同一套判据，
#   判不动就拒），过了才交给 NapCat；出站那一层还有一道同样的闸，两层都不绕。
# 自定义表情查重：on（默认）时 cf_add 添加前多问一次清单（那一道只可能"多问一次"，不会因此拒加）；
#           写「关」（或 off/0/false/no/否）才省掉这一次询问。**缺这一行 / 写错值都按开处理**
#           （失败方向 = 开：更不容易重复添加）。本地账那一道与它无关，永远生效。
