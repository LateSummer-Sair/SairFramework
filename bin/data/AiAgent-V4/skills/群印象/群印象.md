# 群印象（`on_message` 累积 + `on_timer` 蒸馏 + ContextProvider 注入 · 不提供工具）

**这个插件不给模型任何工具**（front matter 里没有 `tool:`，只有 `name`/`description`/`hooks`）。
它做的是 V3 那件「以群号为键记这个群的整体氛围」的事：

- **累积**（`on_message`）：群里每来一条消息，最多只动一次内存；到「回写节流分钟」才开始读 `grouplog`、写自己那一行；
- **蒸馏**（`on_timer`，基板唯一 tick）：按「蒸馏间隔小时 + 最少消息数」判定，用**规则/统计**（词表命中 + 发言人去重 + 2-gram 词频）
  更新友好度 / 氛围 / 话题 / 活跃度 —— **一次模型调用都没有**；
- **注入**（`ContextProvider`）：每轮装配上下文时把「这个群什么氛围」拼成一段 system，
  **只在群聊**出现；氛围差（友好度 ≤ -30）时多给一句态度。

工具/扩展点的识别靠**接口**：`GroupImpressionSkill implements Skill, Hooked, ContextProvider`
（装载器扫这个插件的每个顶层类自动注册；md 里不再声明一遍，见 `notes/lib-declaration.md` 与
`Skills.registerExt` 的类注释）。

## 挂在哪

| 项 | 值 | 为什么 |
|---|---|---|
| 库声明 | `Skill.declare(Libs)` → 表 `group_impression` | 表结构由用到它的插件声明（`notes/lib-declaration.md` 零节）。`call(Args,Host)` 是空实现：本插件没有工具 |
| 事件钩子 | `on_message` | 群消息进来就累积（活跃度/关键词命中）——**只读** `grouplog` 与事件本身 |
| 事件钩子 | `on_timer` | 基板唯一 tick（周期 `conf.tickMs`，出厂 20 秒）；这里按「扫描间隔分钟」降到 10 分钟级 |
| 扩展点 | `sair.v4.ext.ContextProvider` | 只往"进去的东西"里加一段 |
| `stable()` | `false`（**易变段**） | 这一段随群里的消息累积而变（回写会改友好度/活跃度/话题）。放进稳定前缀会让模型服务的前缀缓存每轮失效。注：V3 把群印象放在稳定段（`QQPromptBuilder.java:88-95`），因为它当时只靠"永久累计条数 + 极少先变的友好度"；V4 这条按需求口径走**易变段** |
| `order()` | `50` | V4 现有 provider 是 10（记忆召回）/ 20（用户画像）/ 30（群成员映射）/ 40（情绪）；同序按插件名，顺序确定 = 同输入逐字节可复现 |
| `maxChars()` | 主人配的「预算」（**出厂 500**）—— 你不用去找那个文件 | 基板还要再按全局 `ctxBudgetChars` 截一次。这个接口拿不到 Host，所以用的是"上一次读到的预算"，而 `appliesTo` 是这一轮里最先被调到的，所以第一次出现这段时预算就是对的 |
| `appliesTo()` | `b.group() && b.groupId() > 0 && 启用` | **只在群聊**（私聊没有"群氛围"可言）；返回 false 是正常跳过，基板不记异常 |

## 库表：`group_impression`（每群一行）

| 列 | 类型 | 默认 | 谁写 | 说明 |
|---|---|---|---|---|
| `id` / `ts` | 基板统一补 | — | 基板 | `ts` = 这一行建出来的时间 |
| `group_id` | INTEGER NOT NULL | 0 | 回写 | 群号，**语义上的唯一键**：一个群一行（唯一性口径见下） |
| `group_name` | TEXT | '' | —— | 群名。基板没有"按群号查群名"的只读 `Host` 口径（只能自己调 NapCat 平台动作 `h.napcat().getGroupInfo()`，那要按 op `napcat.get_group_info` 过技能管控表；她本人 `SYSTEM` 恒放行）；本插件**选择不调、不猜**，一般空着（模板里 `{name}` 就渲染成空） |
| `friendliness` | INTEGER | 0 | 回写 + 蒸馏 | 友好度，**-100~100**（V3 同区间）；`<= -30` 就是 V3 的「氛围差」 |
| `activity` | INTEGER | 0 | 回写累加、蒸馏校准 | 活跃度 = 这个群**这辈子**累计条数（V3 `messageCount` 口径）；注入时只印分档标签 |
| `topic` | TEXT | '' | 蒸馏 | 最近话题（几个词，用「、」连接） |
| `atmosphere` | TEXT | '' | 蒸馏 | 氛围短句（按友好度三选一的模板渲染出来，`prompt.md` 的「氛围-差/平/好」） |
| `keywords` | TEXT | '' | 回写 + 蒸馏 | 最近窗口里的命中词 → 次数的 JSON（给注入与观测看；JSON 文本，与基板 `extra/tags` 同一约定） |
| `distill_msgs` | INTEGER | 0 | 蒸馏 | 上次蒸馏时的 `activity` 快照；`activity - distill_msgs` = 还没消化的消息数（蒸馏的判据） |
| `rounds` | INTEGER | 0 | 蒸馏 | 蒸馏轮次 |
| `last_seen` | INTEGER | 0 | 回写 | 这个群最后一条消息的时间（毫秒） |
| `last_write` | INTEGER | 0 | 回写 | 上次回写时间 = **回写节流闸门的持久化那一半**（跨重启仍然有效） |
| `distill_ts` | INTEGER | 0 | 蒸馏 | 上次蒸馏时间（扫描时就按 `distill_ts <= now - 间隔` 挑，走索引） |
| `extra` | TEXT | '' | 蒸馏 | 上一轮的统计明细 JSON：`{ts,sampled,members,negative,positive,score,delta,activity}` |

索引（`LibSpec.idx` 显式给名字，与其它库同一写法）：

| 索引 | 列 | 用途 |
|---|---|---|
| `idx_group_impression_group` | `group_id` | 每群一行的点查（`find`、回写、注入） |
| `idx_group_impression_distill` | `distill_ts` | 扫描"该蒸馏的群"（`_lte` 过滤 + 索引） |
| `idx_group_impression_seen` | `last_seen` | 扫描时按"最近还活跃的群"排序 |

别名：`群印象` / `群氛围`（注册进 `Libs` 后 `store` 工具也能用中文指这张库）；
LIKE 回退列：`topic, atmosphere, group_name`（没有 FTS：这张表不需要全文检索）。

**唯一性口径（老实说）**：`LibSpec.idx()` 只产出 `CREATE INDEX`，**表达不了 `UNIQUE`**，
所以在 DDL 上不加约束，改由写路径保证"每群一行"——`flush` 在**每群一把锁**里做「先查后写」
（`SLOTS` 的 `ConcurrentHashMap<Long,Slot>`，锁在 Slot 上；钩子是按事件 new 实例的，所以状态只能放静态表）。
`find` 若撞见历史残留的多行，取 `id` 最小的那行当主角（幂等、不删别人的数据）。

## 数据从哪来（**只读**，两条）

1. **`grouplog`**（基板写的群聊历史）：**只读**。
   - 条数：`h.store().count("grouplog", {group_id, _gte:{ts: 上次回写}})`（走 `idx_grouplog_group`）；
   - 内容：`h.store().list("grouplog", 同样的 filter, 取样条数, "ts DESC")`（做词表命中与 2-gram 词频）。
   - 为什么条数不拿内存计数器：内存计数器重启就没了，而 `grouplog` 是跨重启的权威事实。
     窗口是 `ts >= 上次回写时间`（首次 = 这个群这辈子全部），所以**不重复计也不漏计**。
2. **事件本身**（`on_message` 的 payload）：判群号/发言人、判有没有被 @（`grouplog` 的 `content` 是纯文本，
   不带 @ 信息，所以"被 @ 负面加权"只对刚到的这条生效）、以及"这个群刚动了一下"。

**本插件绝不写** `grouplog` / `memory` / `dialog` / `pref`（也不建别的表）。写库只有一处：自己的 `group_impression`。

## 一轮群消息怎么走（`on_message`）

```
每来一条群消息：
  ① 不是群聊 / 群号≤0 / 发送者≤0        → return（一个字节都不动）
  ② prompt.md 的 启用 不为 true          → return
  ③ 注册表里没有 group_impression        → return（插件没声明成库 / 表没建出来）
  ④ 本进程第一次见这个群                  → 问一次库上的 last_write（每群一辈子一次 SELECT）
  ⑤ now - last_write < 回写节流分钟      → return（窗口内：只当"这个群刚动了一下"，不写库）
  ⑥ 到点了 → flush（在每群一把锁里）：
       count(grouplog, ts >= last_write)               ← 权威新增条数
       list (grouplog, 同 filter, 取样条数, ts DESC)    ← 取样做信号
       成员分 = clamp(该成员正面命中 - 负面命中, ±每人信号上限)
       信号分 = 各成员分相加；被 @ 且负面 → 该成员多算「被@负面加权」
       友好度 += clamp(round(回写最大幅度 × 信号分 / 信号饱和分), ±回写最大幅度)
       activity += 新增条数；keywords = 本窗口命中词；last_seen = last_write = now
       有行 → update；没有行 → insert（activity 初值 = 这个群这辈子累计条数，distill_msgs = 0）
```

**两条闸门（V3 出处：`EmotionStateManager.noteUnfriendlyGroup`）**：
V3 的注释写得很清楚——旧实现"每收到一条该群消息就 +2 怒"，而情绪衰减只有 −2/分钟，
于是只要群里每分钟有 2 条消息，怒气就被顶到 100 并永久钉死（跨上下文污染）。
V3 的补法是「每群 10 分钟最多联动一次」+「此来源最多把怒气推到 40」。这里的对应物是：

| 闸门 | `prompt.md` 键 | 出厂值 | 作用 |
|---|---|---|---|
| 频率 | `回写节流分钟` | 10 | 同一个群多久最多回写一次库（**不是每条消息写一次**） |
| 幅度 | `回写最大幅度` | 3 | 一次回写最多把友好度推 ±3（推不到极端） |

节流的"快的那一半"在内存（`Slot.lastWrite`），"持久的那一半"在库上的 `last_write`——
所以**重启之后也不会把刚写过的那一行再写一遍**（本进程第一次见某个群时先问一次库）。

## `on_timer` 蒸馏（基板唯一 tick，规则/统计，不调模型）

```
每次 tick：
  ① 启用 / 拿得到 store / 注册表里有这张表     → 否则 return
  ② now - 上次扫描 < 扫描间隔分钟              → return（tick 默认 20 秒，扫描降到 10 分钟级）
  ③ list(group_impression, {_lte:{distill_ts: now - 蒸馏间隔小时}}, 候选群数, "last_seen DESC")
  ④ 逐行：activity - distill_msgs < 最少消息数 → 跳过（消息太少不值得更新）
  ⑤ 蒸馏（每轮最多「每轮群数」个）：
       list(grouplog, ts >= distill_ts, 取样条数, ts DESC) → 统计
       友好度 += clamp(round(蒸馏最大幅度 × 信号分 / 信号饱和分), ±蒸馏最大幅度)   ← 夹在 -100~100
       topic   = 话题词表命中（×话题权重）优先 + 2-gram 频次（≥话题最少次数）补齐，取前「话题上限」个
       atmosphere = 按友好度三选一渲染（氛围-差 / 氛围-平 / 氛围-好）
       activity = count(grouplog, group_id)（这辈子累计，**校准**回写累加出来的值）
       distill_msgs = activity（未消化的消息数归零）；rounds+1；distill_ts = now；extra = 这一轮的统计明细
```

**信号分怎么算（"多个成员印象变差 → 群印象随之变差"的落点）**：
先按**成员**各自封顶（`每人信号上限`，默认 3：一个人刷十句负面最多计 3 分），再把成员分**相加**。
所以"多个成员各自有命中"才压得住群印象：3 个成员各 1 句负面合计只有 −3，与 1 个成员刷满（每人信号上限 3 ⇒ −3）**同值**；
要拉开差距得让更多成员都有命中（3 人各 3 句才是 −9）；「信号饱和分」（默认 6）到顶就吃满幅度
（默认 ±25）。这一步与 V3 的「群内多个成员印象变差时，群印象随之变差」同向，但**来源不同**：
V3 是拿成员的个人印象去联动（V4 里个人印象是 `memory` 里的自由文本，每次统计去解析它既贵又脆），
这里改用**群消息流里的语气信号**做统计口径。

**为什么这里不调模型**：tick 默认 20 秒一次、绝大多数轮什么都不做；要在这里蒸馏就得每 tick 打一次模型，
那是按 tick 烧钱。本插件一次模型调用都没有（`h.ai()` 从来没被用过）。
真要让它"更像人写的氛围描述"，正确的做法是另加一个阈值更高的 `on_timer` 分支（比如"每群每天一次"）
去调 `h.ai()`——代价写在报告里，**本次没做**。

## 注入这一段长什么样

形状照抄 V3 的 `data/prompts/modules/context/impression-group.md`
（`[群印象] 群:{group}{namePart} 友好度:{friendliness} 活跃度:{activity}{atmosphere}`）
与 `impression-group-atmosphere.md`（`- 群氛围: {text}`），标题用中文（`## 群印象`，与
`notes/feel-plugins.md` 第六节 1 的默认做法一致）。渲染出来大概是这样：

```
## 群印象
[群印象] 群:123456 友好度:-12 活跃度:高 话题:加班、游戏
- 群氛围: 平常（友好度 -12；最近 400 条，9 人冒过泡）
```

- 友好度 ≤「友好度差门槛」（默认 -30 = V3 的 `FRIENDLINESS_LOW`）时多一行**态度行**：
  `- （这个群最近不友好：说话简短一点，别主动热络、别硬找话题）` ——
  这就是"氛围差会影响 AI 的态度"。V3 在那一档还会**概率拒答**（`labels/gate.md` 的 `refuse_prob`）并
  反向联动情绪；V4 这里**只写进上下文**：不发消息、不拒答、不改基板的任何判定（拒答属网关行为，
  本插件不碰）。也没有正向态度行（V3 没有，这里不发明）。
- 活跃度是**分档标签**（极高/高/中/低，V3 `activityLabel` 的 5000/500/50），模板里想印条数用 `{activity_n}`。
- 话题为空时自动改用「行模板-无话题」（那条模板里没有 `{topic}`，不会留下一个空标签）。
- 什么都没攒到（没氛围、没话题、友好度 0、活跃度 0）→ 返回空串，这一段**不出现**（与 V3 `hasContent()` 同义）。

## 文案与阈值在哪

全在同目录的 `prompt.md`（`## 配置` / `## 文案` / `## 备注`）：开关、两道节流闸门、蒸馏阈值、词表、
以及注入出去的每一句话。**保存即生效**（惰性缓存 + 按文件 mtime 失效，每轮不读盘）。
Java 里只有结构性字符串（表名/库名/钩子名/列名/日志前缀）与"文件读不到时的兜底默认值"，
**数值**兜底与 `prompt.md` 的出厂值一一对应；`话题词表` 与三条「氛围-*」文案的兜底与出厂值**不同**（文件读不到时话题只剩 2-gram），要改文案请改 `prompt.md`。

## 护栏

- **`h` / `host()` / `store()` / `libs()` 可能是 null**：一律早退或走兜底值，**绝不抛异常**；
  钩子与 provider 的整个身体都包在 `try/catch (Throwable)` 里（异常只记一行 `[群印象] …`）。
- **库不存在**（插件没声明成库 / 表没建出来）：`hasLib(h)` 先问注册表，直接早退 —— 不刷 `[store] 未知库` 那种噪音。
- **只写自己的表**：写路径只有 `flush` 与 `distill`，都写 `group_impression`；`grouplog` 只有
  `count`/`list` 两种只读调用。
- **不越权**：它**不注册工具**（md 里没有 `tool:`）⇒ 技能管控表里没有它的 op、也没有它的行；
  钩子与 provider 都由基板派发、按 `SYSTEM` 主体跑（她自己的自主行为，恒放行），所以这里没有
  （也不需要）任何 op 判定；读写面只有两个：读 `grouplog`、写自己的 `group_impression`；
  不发消息、不派子 Agent、不碰基板配置。
- **只在群聊出这一段**：`appliesTo` 判 `b.group()`；`build` 里再判一次（双保险）。
- **成本上界**：每条群消息 = 1 次 map 查（窗口内）或 1 次 `count` + 1 次 `list` + 1 次 `update`（每群每 10 分钟）；
  每 10 分钟 = 1 次 `list` 挑候选群 + 至多 3 次蒸馏（每次 2 次读 + 1 次写）。

## 验收（自检怎么跑）

不在工程里的冒烟（临时 SQLite + 假 Host + 假事件）验这些断言：

1. 种子 40 条群聊 → 一条群消息触发回写 → 一行 `group_impression` 被建出来（`activity` = 这辈子累计条数）；
2. 再补消息、`on_timer` 一次 → 群印象**被更新一次**：`rounds=1`、`distill_ts>0`、`atmosphere` 非空、
   负面词命中时 `friendliness < 0`、`topic` 非空；
3. **节流生效**：同一群短时间内第二条消息不写库（`last_write`/`activity` 不动）；
   把 `回写节流分钟` 改成 0（不节流）后同样的第二条消息**会**写库 —— 证明"是节流挡住的，不是别的";
4. **跨重启的节流**：另起一个 JVM（内存闸门清空）再发一条消息，仍然不写库（库里 `last_write` 还新）；
5. 注入行**只在群聊**出现（私聊 `appliesTo=false` + `build` 返回空串）；
6. `host()==null`、`store()==null`、注册表里**没有这张表**、`libs()==null` 四种情况都不抛异常（这段安静消失）；
7. md 的 front matter **没有 `tool:`** 且 `hooks` 正好是 `[on_message, on_timer]`（用基板自己的
   `SkMd.parse` + `Skills.hooksOf` 读，不是拿眼睛看）；
8. `group_id` 唯一：同一个群连发多条消息（含"每轮群数/候选群数"都走到）之后表里仍然只有一行。

出事了看哪里：控制台 `[群印象] 回写 …/蒸馏 …`（`logConsole` 开 `skill` 类别的 dim 行）、
`status.ext` 里 provider 的 `chars/ms/errors/timeouts`、以及 `store` 工具读 `group_impression`。

## 已知限制（如实记）

1. **不调模型**：氛围/话题是"词表 + 词频"的统计结论，不是人话总结。想更像人写的，得另加一条更稀疏的
   模型分支（见上「为什么这里不调模型」）。
2. **词表是子串命中**：`滚` 会命中"滚烫"。词表按群调；这是"规则蒸馏"的固有代价。
   话题的 2-gram 兜底也会带出跨词碎片（冒烟里就见到 `个群` 这种，出自"这个群真垃圾"）——
   用 `话题停用词` 压，或者干脆把 `话题词表` 配全，让话题只从词表里出。
3. **`group_name` 基本是空的**：基板没有"按群号查群名"的只读 `Host` 口径（`get_group_info` 只能自己调 NapCat
   （按 op `napcat.get_group_info` 过技能管控表；她本人 `SYSTEM` 恒放行），又是一次连接面动作），本插件不猜 —— 模板里的 `{name}` 一直是空。
4. **同一毫秒的边界**：窗口用 `ts >= last_write`，正好落在边界那一毫秒的消息可能被多计 1 条
   （没有 `_gt` 控制键，只有 `_gte`）。量级可忽略，且蒸馏时 `activity` 会被 `count(group_id)` **校准**回真值。
5. **`grouplog` 被基板维护清掉之后**：窗口读不到行时只推进闸门（`distill_ts`/`distill_msgs`），不编数据。
6. **进程内 `SLOTS` 无上限回收**：表大小 = 进程里见过的群数（与基板别的内存缓存同一量级）；
   进程重启即清空。
7. **友好度只由"语气信号"驱动**：被骂会掉、被夸会涨，但"群里发生了好事/坏事"（与语气无关的事实）读不出来。
8. **不做拒答、不联动情绪**：V3 的 `refuse_prob` 与 `noteUnfriendlyGroup` 属网关与情绪面，
   V4 没有情绪表，本插件只影响上下文里的态度。
