# 申请审批（`on_request` 钩子技能 —— 钩子是她自己的自主行为 = `SYSTEM`，不提供工具）

基板把好友申请 / 群邀请原样交给 `on_request` 钩子；**基板自己不带审批策略**，策略全在这个技能里。删掉技能 → 申请不再被记录、也没人通知主人（基板只打一行"没有技能接管这条申请"）。

钩子派发时主体是 **`SYSTEM`**（她自己的自主行为，见 `Skills` 的 `dispatch(hook, payload)` → `hookActor()`），
所以自动同意 / 私聊通知这些平台动作走得通 —— **这是"她自己的自动策略"，技能管控表对她恒放行**，
也没有"谁触发了申请"这一层判定；`h.caller()` 只是申请人这个**事实**（给她写通知文案用）。
本技能**不提供工具**（md 里没有 `tool:`）⇒ **没有 op 要判**：它走的全是钩子（跑在 `SYSTEM` 主体上），
也没有任何旧的判定调用需要替换。
非主人**手动**同意/拒绝申请则是另一回事：那是「待处理申请」技能的事（它调 `napcat` 动作，按自己的 op 授权判定，未授权一律拒）。

## 策略（默认保守）
| 事件 | 处理 |
|---|---|
| 好友申请 `request_type=friend` | **好感度 ≥ `好友自动同意好感度`（默认 100 = 眼熟档；0/负数 = 关）⇒ 自动同意**（`setFriendAddRequest(flag, true)`）+ 默认私聊主人一条；没到门槛 ⇒ **只记录、绝不自动同意**（与老口径逐字一致：把 `flag/qq/comment` 记进 `kv`，**默认不私聊主人**，要提醒就开 `通知主人: true`）。同意与否都归主人可查，也可以直接用 `napcat` 工具的动作 `set_friend_add_request` |
| 群邀请 `request_type=group` + `sub_type=invite` | 三条**或**（按此顺序判，事实行会写明是哪一条）：① 邀请人就是主人（`masterQQ`，开关 `自动同意群-主人邀请`，默认 `true`）⇒ 自动同意；② **邀请人的当前好感度** ≥ `群邀请自动同意好感度`（默认 300 = 朋友档；0/负数 = 关）⇒ 自动同意；③ 群号在 `自动同意群` 白名单里 ⇒ 自动同意。三条都不成立 ⇒ **只记录**（要提醒就开 `通知主人: true`）。**自动同意之后默认私聊主人一条**（`同意后通知主人` 默认 `true`） |
| 群申请 `request_type=group` + `sub_type=add` | **一律不自动同意，只记录**（可能是提醒）。`add` = 别人申请进她管的群，`invite` = 邀请她进群；把 `add` 也自动同意 = 放陌生人进群，所以白名单也不豁免 |
| 其它 request_type | 不处理，只进控制台日志 |

## 配置与文案在哪
全在 `prompt.md`（同目录）：
```
启用: true                       # 不为 true 则整个技能不动作
自动同意群:                      # 群号白名单，逗号分隔；留空 = 不按白名单自动同意
自动同意群-主人邀请: true        # 默认 true = 主人亲自邀请就自动同意（与下面两条并列，不是二选一）
好友自动同意好感度: 100          # 默认 100（眼熟档）；0/负数 = 关；留空 = 0 = 关
群邀请自动同意好感度: 300        # 默认 300（朋友档）；邀请人当前好感度 ≥ 它 ⇒ 自动同意；0/负数 = 关；留空 = 0 = 关
通知主人: false                  # 出厂 false = "没自动同意、只记录"时不私聊主人；要用就改成 true
同意后通知主人: true             # 默认 true = 自动同意之后私聊主人一条；留空/false = 不打扰
好友通知: …                      # 只记录时的提醒文案（占位符见下）
群邀请通知: …                    # 不在白名单时的提醒文案
自动同意通知: …                  # 旧键：白名单群自动同意后的文案（同意群通知 留空时回落到它）
同意群通知: …                    # 群自动同意后的文案
同意好友通知: …                  # 好友自动同意后的文案
```
占位符：`{name}` 申请人昵称、`{qq}`、`{group}` 群号、`{subtype}` add/invite、`{flag}`、`{comment}` 验证信息、
`{favor}` 好感度值（现读的当前好感度）、`{need}` 本次自动同意的阈值（好友通知 = 好友门槛；
群通知只在"好感度达标"那一支给值 —— 主人邀请 / 白名单没有阈值，渲染成空）、`{level}` 好感度档位名。
**文案留空、或对应开关没开，就不发那条通知**（技能里没有写死的用户文案；出厂默认 = 申请来时不打扰，这时记的 `action` 是 `recorded`）。
**通知只在"审批之后"发生，发送失败只记一行日志、绝不影响审批结果。**

## 落库 / 观测
| 键 | 内容 |
|---|---|
| `kv.approve_friend_last` | 最近一条好友申请 JSON：`{ts,type,qq,flag,comment,action,whitelisted}` |
| `kv.approve_friend_count` | 好友申请累计条数 |
| `kv.approve_group_last` | 最近一条群邀请/加群 JSON：`{ts,type,group,qq,flag,subtype,comment,action,whitelisted}` |
| `kv.approve_group_count` | 群邀请累计条数 |
| 控制台 | `[申请审批] …` 日志（含通知发送结果、NapCat 未连接等） |

`action` 取值：`recorded`（只记录：通知文案为空 **或 `通知主人` 没开**，或没到自动同意的条件）、`notified`（已通知主人）、`auto_accept`（已自动同意：主人邀请 / 邀请人好感度达标 / 白名单群邀请 / 好友好感度达标）、`accept_failed:<原因>`（自动同意失败）、`notify_failed`（想通知但发送失败）、`offline`（NapCat 未连接，只能记录 / 自动同意做不了）。

控制台里"自动同意"那一支各有一行结构事实（**写明是哪一条判据**）：
`→ 自动同意（主人邀请）通知=ok|off|failed`、
`群 N 在白名单里，已自动同意（flag=…）通知=…`、
`→ 自动同意（好感度 350 ≥ 300）通知=…`（群邀请，邀请人好感度那一支）、
`→ 自动同意（好感度 250 ≥ 100）通知=…`（好友申请，申请人好感度那一支）；
"只记录"那一支是 `→ recorded（不在白名单）` / `→ recorded（不是群邀请，不自动同意）` /
好友的 `→ recorded（不自动同意）`。

## 说明
- "不落库地记进 kv" = 不进六库（不污染 `note/memory`），只用基板运行表 `kv` 存一条可查的记录。
- NapCat 未连接时无法通知主人，也不会自动同意（动作会回「Napcat 没有连接」）——此时只记录 + 控制台日志，等主人上来处理。
- **反馈与审批分开**：自动同意一旦发生就是既成事实，`同意后通知主人` 关掉、或那一条私聊发失败，都不会回滚审批（`action` 仍是 `auto_accept`）。
- 好感度读自宿主只读视图 `Host.favor()`（`of(qq)` 现读当前值 / `levelName`）；技能自己**不记账、不写好感度**；
  读不到按 **0（档位名「初识」；`>0` 才是「陌生」）** 处理，fail-safe 不自动同意。
- 两个好感度阈值键（`好友自动同意好感度` / `群邀请自动同意好感度`）**留空 = 0 = 关**，只有键整个缺失才取出厂默认值
  （它们开着就会自动放人进来，所以"没写值"按最保守处理）。
- `自动同意群-主人邀请` 关掉之后，**主人的邀请不再用"他的好感度"兜一遍**（那个开关就是"别自动同意他的邀请"）；
  主人的邀请仍可走白名单那一条。
- 处理完置 `payload._handled = true`，表示这条申请本技能接管了。
