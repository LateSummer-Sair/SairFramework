# 群成员映射（ContextProvider · 稳定段）

**这个插件不给模型任何工具**（md 的 front matter 里没有工具声明，只有 `name` 与 `description`）。它只做一件事：
每轮装配上下文时，把「这个群里谁是谁」拼成一段 system 注入进去 —— 群名片（空则昵称）↔ QQ、角色。
工具/扩展点的识别靠**类实现了 ext 接口**（`GroupMemberMapProvider implements ContextProvider`），
基板装载时会扫这个插件的每个顶层类并自动注册，不需要在 md 里再声明一遍。

## 挂在哪

| 项 | 值 | 为什么 |
|---|---|---|
| 扩展点 | `sair.v4.ext.ContextProvider` | 只往"进去的东西"里加一段 |
| `stable()` | `true`（**稳定段**） | V3 里这段本来就在稳定段：`QQPromptBuilder.java:63-64` 的稳定段顺序是「技能索引 → 群印象 → 群身份 → **群成员映射** → 结构化偏好 → 用户画像 → 会话日志」。V4 的差距就是它没了 |
| `order()` | `30` | V4 现有的两个 provider 是 10（记忆召回）/ 20（用户画像）；同序按插件名，顺序确定 = 同输入逐字节可复现 |
| `maxChars()` | `prompt.md` 的「预算」（默认 **800**） | 基板还要再按全局 `ctxBudgetChars`（默认 6000）截一次 |
| `appliesTo()` | `b.host() != null && b.group() && b.groupId() > 0` | **只在群聊**；私聊没有"群成员"可言；拿不到 NapCat（`host()==null`）也别出这一段。返回 false 是正常跳过，基板不记异常 |

**排序稳定**这条纪律 V3 自己也踩过：`UnifiedQQMemoryManager.java:894-896` 写着「固定顺序：`updated_at`
会随群里每次发言被刷新，按它排序会让「群昵称映射」这段稳定前缀的字节每次都可能变，打断 KV 前缀缓存」
（于是 V3 改成 `ORDER BY nickname ASC, user_id ASC`）；角色表同理（`:1152-1153`「避免 `updated_at` 抖动导致
提示词字节漂移」，`ORDER BY role='owner' DESC, user_id ASC`）。本插件把这条纪律固化在**代码**里（不是配置里）：
排序键 = `角色 → QQ → 名片+昵称`，三个键都是成员的固有属性（见下一节）。

## 「同输入逐字节不变」是怎么保证的

1. **排序键全是不变字段**：`roleRank(owner=0,admin=1,member=2,未知=3) → qq 升序 → card+nick`。
   没有任何"谁最后发言/什么时候进群/什么时候取到的"参与排序 —— **数据里也根本没有时间字段**
   （`M` 这个类只有 `qq/card/nick/role`，解析时 `join_time`/`last_sent_time` 一律不读）。
2. **不写时间、不写随机、不读本轮正文、不看说话人**：`build()` 不看 `b.text()`，渲染层不提供 `{time}` 这类占位符，
   `render(...)` 的签名里**没有调用者信息**（谁在说话不影响这一段）——这一点是刻意设计，见「已知限制」第 1 条。
   文案里也没有任何随轮次变化的东西。
3. **快照不可变**：一段文本只由「`Cache.Entry` 里那份快照 + 一份配置」决定。同一份快照渲染多少次都是同一串字节
   （`render(...)` 是纯函数：不读盘、不查网、不看时间）。
4. **去重与截断也是确定的**：同 QQ 只会留一行（先排序，故留下的是角色最高的那行）；
   截断只从尾部丢 —— 丢掉的永远是"角色最低、QQ 最大"的那些人。
5. 配置本身（`prompt.md`）变了会让"同输入"变成"输入变了" —— 这是允许的，代价是下一次装配前缀全变一次。

## 数据从哪来（**只读**）

只用 `Host` 能力面：

1. **群成员表**：`h.napcat().call("get_group_member_list", {"group_id": <群号>})` → 响应 `data` 数组，
   每项读 `user_id` / `nickname` / `card` / `role`（动作名可在 `prompt.md` 里改）。
   `h.napcatConnected()` 为 false 时**连查都不查**。
2. **跨群昵称**：V4 没有 `group_nicknames` 这张表（`notes/v3-migration-map.md:128`：V3 的成员/昵称三张表
   V4 无落位），所以这里用**插件自己的内存**被动累积：每次真查到一批群成员，就记下「QQ → 最近一次的称呼」。
   **不额外查 NapCat**、不建表、不落盘。V3 的对应物是 `getPersonalNicknameMap()` + `title.global-nickmap`。
3. **缓存**：`ConcurrentHashMap`（按群 + TTL），进程内，重启即空。

**不建库、不写库、不自己开库、不写 SQL**；`BuildContext.subagent()` 为真时同样没有任何写路径
（这个插件整体没有副作用）。

### 权限闸门：两种结果都要能容忍

`Host.napcat()` 是**带闸门**的接口（`Boot` 里装配好的 `guardedApi`）：`Api.Guard` 按
`Ctx.caller()` 判这个动作的 **E 类（对外）`X` 位** —— `get_group_member_list` 是 QQ 平台动作，
就是 `Res.platform("get_group_member_list")`。按类默认分配：`MASTER` 恒全权、`SYSTEM` 的 `E = RWX`（`Acl.SYS_E = Bits.ALL`）、
`ALLUSER` **E 无**（要放开只有主人在账本 `perms.json`（v3）里写例外条目）。
闸门只看**调用线程的 `Ctx` 绑定**，而这有两种情形：

- 基板把扩展点放在自己的扩展工作线程（`v4-ext-N`）上跑 —— 那个线程上 `Ctx` 被**显式绑成当轮调用者**
  （`ExtRegistry.guarded`：有触发者就绑触发者，没有触发者才按 `SYSTEM` 判），所以普通用户来问时这一支也按他判；
- 扩展点线程池满时退回 caller-runs（调用线程直接跑），此时 `Ctx.caller()` **有绑定**，
  普通用户（`ALLUSER`）会拿到带 `[权限阻断]` 标识的拒绝文案（缺 `get_group_member_list` 的 `X` 位）。

所以两种结果都可能出现。本插件对**任何一种"拿不到"**都做同一件事：`parse()` 见到响应里的 `error` 字段
（权限阻断 / `Napcat 没有连接` / 超时 / 非 JSON）就返回 null → **这一段不出现**，不抛异常、不重试轰炸
（失败也进缓存，压「失败缓存秒」）。**这一条是本插件的硬口径，与"谁在说话、身份是谁"无关。**

如实说明当前生效的是哪一支：本插件的查询跑在**它自己的守护线程**上（见下一节），那个线程**没有 `Ctx` 绑定**，
`Guard` 才按 `SYSTEM`（她自己的自主行为，E `RWX`）放行 —— 所以真机上生效的是"放行"那一支（拿得到成员表）。
若哪天基板改成"扩展点也按调用者裁决"，或者查询被挪回调用线程，结果就是上面那句 `[权限阻断] …`，
此时本插件安静降级（这一段不出现），不会报错、也不会绕。**换句话说：容忍是硬要求，拿到数据是运气好。**

## NapCat 查询不占基板的 200ms

基板给每个扩展点的预算是 `extTimeoutMs`（默认 **200ms**），超时就丢掉这一段并**打断**线程。
`get_group_member_list` 是阻塞调用（大群可能几百毫秒），同步查会被打断在半路 —— 白查一次，还多一行 timeout。

所以查询放在**插件自己的后台守护线程**上（1 个线程 + 16 长度有界队列 + 同群在飞去重 + 队列满直接丢弃）：

- **冷缓存**（这个群第一次见）：这一轮先不出这一段，数据回来后的下一轮就出；
- **缓存过期**：先出旧快照，后台换新（stale-while-revalidate）——
  这一段的字节因此在一个缓存窗口内是常量，跨群的增量也只会在本群下一次刷新时才进来；
- `build()` 里**没有网络调用、不等于"零开销"**（查询在后台线程上）；本插件自己的 `prompt.md` 读法是"每轮 stat + mtime 变了才整读"，所以永远不会踩到那 200ms。

这条做法也是 V3 原样：`QQPromptBuilder.java:22-35` 的 `bgFetchPool`（1~2 个守护线程 + 有界队列），
V3 的注释写得很直白 —— `getGroupInfo`/`getFriendList` 这类阻塞调用不能丢进 AI 主链路，
「一次卡住的 NapCat 调用就会吃掉 1/3 的 AI 处理能力」。

## 文案与阈值在哪

全在同目录的 `prompt.md`（`键: 值`，`#` 开头是注释）：

| 键 | 出厂值 | 作用 |
|---|---|---|
| `开关` | `true` | false = 这一段整轮不出现（不查 NapCat） |
| `动作名` | `get_group_member_list` | OneBot v11 动作名 |
| `人数上限` | `20` | 本群最多印几个人 |
| `全局昵称上限` | `15` | 跨群那段最多印几条 |
| `全局昵称开关` | `true` | false = 不出「跨群昵称映射」 |
| `缓存秒` | `60` | 同群多少秒内不重复查 |
| `失败缓存秒` | `30` | 查失败也压这么久（不轰炸） |
| `单名上限` | `24` | 一个称呼最多多少字（防超长名片吃光预算） |
| `预算` | `800` | 本段字符上限 = `maxChars()` |
| `标题` / `说明` | `## 群成员映射` / 无图标=普通成员… | 本群小节 |
| `行模板` | `- {name} (QQ {qq}) {role}{mark}` | 一人一行 |
| `全局标题` / `全局行模板` | `## 跨群昵称映射` / `- {name} (QQ {qq}) {role}{mark}` | 跨群小节（形状与本群一致；跨群只记名字不记角色，`{role}` 一律「成员」） |
| `角色名` | `owner=群主,admin=管理员,member=成员` | 角色中文词表 |
| `群主标记` / `管理员标记` | `👑` / `🔧` | 可见标记（没有 ⭐，见「已知限制」1） |
| `无名占位` | `未知` | 名片与昵称都空时的替代值 |

Java 里只留"文件读不到时的兜底默认值"，兜底值与 `prompt.md` 的出厂值一一对应。
读法是**惰性缓存 + 按 mtime 失效**：每轮不读盘，改完保存下一轮生效。

## 护栏

- `host()` 可能为 null、`napcat()` 可能为 null、NapCat 可能没连、动作可能被权限阻断、响应可能不是 JSON、
  成员项可能缺字段、名片可能带换行或超长 —— 每一种都**自己吞掉并降级**（返回空串 = 这一段不出现），
  `build()` 外层还有一层 `catch (Throwable)`。
- **超时**：`build()` 不查网（查询在插件自己的守护线程上），所以基板的 200ms 预算够；
  后台线程是守护线程（不挡进程退出），队列有界，满了丢弃这一单、下一轮再说。
- **预算**：先按「人数上限」截人，再按「预算」**整行**丢尾巴（先丢跨群、再丢本群）；
  一行的最小单位是"一个人"，不切半行。极端配置下连一个人都放不下就整段不出（宁可没有，也不出空壳标题）。
- **异常隔离**：不抛异常、不打日志刷屏（每轮都调，诊断行走基板自己的 `[ext]` 行）、不派子 Agent。

## 验收（对应探针断言）

1. **假 NapCat 返回成员表 → 上下文出现 ≤「人数上限」的映射行**：25 个成员时只有 20 行（角色在前、QQ 升序）；
   `notes/feel-plugins.md:188` 的原话就是这条；
2. **稳定段逐字节不变**：同一份快照连续 build 两次字符串完全相等；**换个人（不同 QQ / 主人）来问，
   同一群的这一段仍然逐字节相同**（排序键、缓存快照、无时间字段、不看说话人；私聊根本不出这一段，见下面第 5 条）；
3. **缓存命中不重复查**：`缓存秒` 内第二次调用不再发起 NapCat 查询（假对象计次不变）；
4. **安静降级**：`host()==null` / 私聊 / NapCat 返回权限阻断文本 —— 三种情况都返回空串且不抛异常；
5. **只在群聊**：私聊与 `host()==null` 时 `appliesTo()` 直接返回 false（基板不会记成异常）；
6. **配置生效**：把 `人数上限` 改成 3（保存后 mtime 变化）→ 下一轮只有 3 行；
   关 `开关` → 这一段整轮不出现。

## 已知限制（如实记）

1. **没有 ⭐主人标记（刻意不做，不是漏了）**：V4 没有"主人 QQ 清单"的只读口（V3 有 `AiConfig.getMasterQQs()`），
   唯一能拿到的是"当前说话人是不是主人"（`b.master()`）。可以想象的做法是"说话人自己是主人就给他那行加 ⭐"，
   但那会让同一群、同一批成员的这一段的字节**随谁在说话而变** —— 主人一开口，整段稳定前缀的缓存就废一次。
   V3 的 `roleMarks` 是按"主人**集合**"标的，与谁在说话无关，所以它当年能安稳待在稳定段。
   这里选择**纪律优先**：`{mark}` 只看成员自己的角色（👑/🔧），渲染函数签名里干脆没有调用者信息。
   将来若基板补一个"主人 QQ 只读口"，加回来是几行的事，而且加回来也不会破坏稳定段。
2. **冷缓存那一轮不出这一段**：第一次见到某个群时是"后台查、下一轮出"。真人聊天里看不出来（轮次密集），
   但"第一条消息就想要映射"的场合会差一轮。
3. **跨群小节会随观测面缓慢增长**：它是被动累积的（见到新人才会多一条），且上限 15 条按「角色 → QQ → 名字」排序截取（跨群项角色恒为成员，所以实际就是按 QQ 升序）——
   新人进来时这一段会变一次（一次性的低频变化，不是每轮抖动）。想彻底避免就关 `全局昵称开关`。
4. **跨群结构体与 V3 不完全等价**：V3 的全局映射来自 `group_nicknames` 表（谁在哪个群说过话）；V4 没有这张表，
   这里只有"这个进程见过的人"。V4 的等价物本来就不存在，这一节属于"照 V3 的精神补的形状"。
5. **失败也进缓存**：权限阻断/超时会压住 `失败缓存秒`，所以"NapCat 刚恢复"到"这一段回来"最多差 30 秒。
