# 视觉识图（工具 `vision`；读数据目录内的图 = B 类的 `R`（非主人无位 ⇒ 读不到），调模型 = T 类的 `X`）

一个 op：`see`。把图交给基板的 DeepSeek 客户端（`h.ai().vision(...)` + `Msg.userWithImages`），
**自己不下载、不落盘、不建表**：URL 原样给模型，本地文件读成 `data:` URL，fileid 由 NapCat 解析。

权限上只有两件事：读**数据目录内的本地图片**判 B 类的 `R`（`VisionSkill` 读字节前的 `needPath(f,'R')`；
B 类对非主人无位（∅）⇒ 读不到；图落在 `files/` 里时属 C、无专有位 ⇒ 非主人只读（`R`），读得到），
**调外部模型**属工具的运行时（T 类的 `X`，`VisionSkill` 入口判的 `Res.tool("vision")`，
`ALLUSER` 默认 `T=无` ⇒ 非主人用不了这把工具，要特例放行）。
**普通人发来的图她照样能看到** —— 主要走 ① 事件里的图片 URL / ② `get_image` 的 http 链接 / ③ base64
这三条路（`byFileId` 的前三级），它们**不判路径位**；**没有好感度门槛**（好感度不再决定任何权限）。
唯一会变的是第 ④ 级：**NapCat 缓存路径兜底不做数据目录前缀校验**，落在数据根之外时算 **A 类**，
而 A 类的默认分配对普通人已**全部收回**（连 `R` 也不给）⇒ 这条兜底对非主人会被拒（按"临时失败"处理、
不拉黑、不重试轰炸）；她自己的自主行为（`SYSTEM`）A 类仍是 `R`，主人恒全权，照常读。

## `see` 的三种图源

| 形状 | 怎么认 | 怎么给模型 |
|---|---|---|
| `http(s)://…` | 开头就是协议 | **先过基板 SSRF 闸门**（`kit/NetGuard`），过了才把链接原样给模型 |
| `data:image/…` | 已经是 data URL | 原样 |
| NapCat `fileid` | 没有路径分隔符、没有盘符/协议，且数据目录里没有同名文件 | ① 事件里的图片 URL（跨机可取）→ ② `get_image` 的 http 链接 → ③ `get_image` 的 **base64** → ④ 本地缓存路径直读（只当同机快路径） |
| 本地路径 | 其它情况（相对路径按数据目录解析，`file:` 前缀也认） | 读字节 → `data:image/…;base64,…` |

**本地路径必须落在数据目录里**（canonical 路径前缀校验，`..` 与符号链接都逃不出去）；
越界直接拒绝，不读、不看、不写。NapCat 自己返回的缓存路径不受这条限制（它不是模型给的输入），
但同样要过"是文件 / 不是空的 / 没超上限 / 认得格式"四道。

### fileid 为什么要按这个顺序（跨机部署）

NapCat 与插件**不同机**时，`get_image` 只会给出 **NapCat 那台机器**上的本地路径，插件机读不到。
所以顺序是：**先把事件里那条图片 URL 用起来**（基板在收到消息时会记一笔 `Inbound`：图片段的
`file` 值 → 可直连的 `url`，进程内短期缓存、不落盘），其次才是 `get_image`（http 链接 / base64），
最后才是"本地路径直读"这条**同机快路径**。

- 事件 URL 命中时**根本不需要** `get_image`（少一次 NapCat 往返，跨机也能取到图）；
- 纯 ASCII 的图片地址会被闸门挡在内网之外（`fileid` 取回的 URL 同样过闸门）；
- **路径读不到不算永久失败**：见下面的黑名单口径。

## 缓存与黑名单（都在 `store.kv`，键前缀 `vision:`）

| 键 | 内容 | 生命周期 |
|---|---|---|
| `vision:cache:<md5(图+问题)>` | `{ts,text,image,model,ms}` | 超过 `缓存小时` 视为过期（不删，读的时候忽略） |
| `vision:bad:<md5(图)>` | `{ts,code,reason,image}`（`code` 是结构标记，`reason` 是给人看的说明） | **永久**：命中就直接回说明，不再打模型 |
| `vision:last` | 最近一次的状态 JSON | 覆盖写，纯观测 |

**哪些算永久失败**：**模型/用户给的**本地路径不存在 / 读不出来 / 空文件 / 超 `最大图片字节` /
认不出图片格式。这些是"这张图本身有问题"，重试一百次也一样，所以进黑名单。

**哪些是临时失败（绝不拉黑）**：`get_image` 取不回、NapCat 侧路径读不到（**跨机就是这种情况**）、
base64 解不出、图片地址被 SSRF 闸门拒、没配 apiKey、模型报错、模型返回空。
临时失败只回 `prompt.md` 的「读不到临时」/「内网拒绝」说明并把 `vision:last` 记成 `temp:true`，
下次照样重试 —— 换台机器、等缓存落盘、改用图片 URL 都可能救回来。

## 模型与 key

- key 来自基板配置（`h.ai().apiKey()`）；为空时**不打网络**，直接回一句"模型没配 apiKey"的说明；
- 模型名默认用基板模型（`conf.resolveModel()`，`auto` 就是默认模型，没有路由）；
  想单独指定多模态模型就在 `prompt.md` 里写 `视觉模型:`，它会覆盖这次请求的 `model` 字段；
- 模型名不支持图片输入时会回空内容，这种情况给的是"模型没给出内容，可能不支持图片"的说明
  （提示词与说明文案都在 `prompt.md`）。

## 主模型不会看图时的兜底（派子 Agent 用会看图的模型）

**触发条件**（`VisionSkill` 里的 `see` 分支）：基板模型被判定为"不会看图"
（`CtxBuild.looksVisionCapable(conf.resolveModel(), conf.visionModels(), conf.visionModel())` 为假 ——
即"硬白名单 + 配置追加项"整套判据，`ctx\CtxBuild.java:198-213`；R3 起两个追加项走 `ConfView.visionModels()` /
`ConfView.visionModel()`，与 `CtxBuild.selfHasVision` 同一个默认值来源）**且**基板配置里有独立的视觉模型
（`conf.visionModel()` 非空）—— 两条都满足才走兜底；否则就是常规的多模态直连（上一节）。

| 这一路的输入 / 输出 | 说明 |
|---|---|
| 谁是执行者 | `h.spawn(任务, null, false, 简报, 视觉模型)`：**同步**（`async=false`）派一个子 Agent，模型换成视觉模型 |
| 简报 | `prompt.md` 的 `兜底说明`（角色与要求：完整描述、不臆造） |
| 任务 | `prompt.md` 的 `兜底任务`，含两个占位符：`{ask}` 用户问的问题、`{url}` **这次要看的图**（URL / `data:` URL 都是它） |
| 成功 | 取子 Agent 的回执正文当结果返回（**不进缓存**，因为这一路的模型与直连不同），`vision:last` 记 `fallback:true` + 用的模型 |
| 失败 | 回 `prompt.md` 的 `兜底失败`（含模型名与错误串），`vision:last` 记 `ok:false`+`fallback:true`；**不拉黑这张图**（环境问题，不是图的错） |
| 不触发时 | 主模型自己会看图 ⇒ 走常规直连；`视觉模型` 留空 ⇒ 也不走兜底（没有可用的看图模型，直连失败就回"模型没看清"） |

> 两个坑（改 `prompt.md` 时别踩）：① 三个键的名字是 `兜底说明` / `兜底任务` / `兜底失败`（技能按中文键取），
> 改名就等于让文案退化成 ASCII 占位符；② 值按**一行一条**读，`兜底任务` 必须写在同一行里 ——
> 换行会被当成"没有冒号的行"丢掉，`{url}` 一丢子 Agent 就看不到图了。

## 边界与取舍

- **不当作 OCR**：要读字也是问模型，不调 `ocr_image`（那是 NapCat 的活，归 `napcat` 工具）；
- **不转存**：本地图只在内存里读成 base64，不落 `files/`；
- **黑名单是"永久"的**：唯一的出口是显式 `refresh=true`（重试成功后自动摘掉）；
- **删掉即消失**：技能目录整体删掉，`vision` 工具就没了，缓存与黑名单的 kv 仍然留在库里。
